Implemente uma REESTRUTURAÇÃO CONTROLADA DO CARREGAMENTO das 4 personas do AgroRisk.

Esta alteração deve resolver de forma definitiva o problema de UX causado
por telas aguardando cálculos e enriquecimentos externos.

IMPORTANTE:
o objetivo NÃO é fazer 500 operações calcularem mais rápido.

O objetivo é:

1. mostrar a tela imediatamente;
2. calcular primeiro SOMENTE o risco que o usuário está vendo;
3. carregar o restante somente quando necessário.

NÃO criar nova arquitetura de Risk Engine.
NÃO retreinar ML.
NÃO alterar fórmula.
NÃO alterar thresholds.
NÃO alterar pesos Sompo.
NÃO alterar banco/schema.
NÃO alterar Vite.
NÃO alterar V1.

EU faço os commits Git manualmente.

NÃO executar:
git add
git commit
git push
git merge
git rebase
git reset

==================================================
PRINCÍPIO ARQUITETURAL OBRIGATÓRIO
==================================================

Toda informação deve pertencer a uma destas 3 classes:

1. IMMEDIATE
2. PRIORITY
3. ON_DEMAND

Não criar quarta estratégia paralela.

--------------------------------------------------
IMMEDIATE
--------------------------------------------------

Dados necessários para montar a tela e permitir navegação.

Devem vir prioritariamente do PostgreSQL.

NÃO podem depender de:

- Open-Meteo
- OpenTopography
- Open-Elevation
- Overpass
- Risk Engine V2
- score de outras operações

A primeira tela deve aparecer assim que esses dados estiverem disponíveis.

--------------------------------------------------
PRIORITY
--------------------------------------------------

É o risco da operação/entidade que o usuário está vendo.

Após a primeira renderização:

→ calcular UMA operação prioritária;
→ prioridade interactive;
→ devolver resultado assim que terminar;
→ atualizar imediatamente a UI.

NÃO esperar batch secundário.

--------------------------------------------------
ON_DEMAND
--------------------------------------------------

Tudo que não é necessário naquele momento.

Exemplos:

- rankings completos;
- operações de páginas não visíveis;
- outros clientes;
- histórico detalhado;
- scores de máquinas não abertas;
- distribuições completas;
- recomendações secundárias.

Somente calcular quando a tela/aba/detalhe exigir.

==================================================

PRESERVAR esse comportamento.

IMMEDIATE:

- clientes
- máquinas
- áreas
- operações
- alertas persistidos
- manutenção
- atividade recente
- navegação
- contagens PostgreSQL

Fase A

→ resultado publicado imediatamente

Não esperar lote de 12 para exibir primeiro score.

Corrigir também:

- se request prioritário falhar, permitir retry;
- não deixar IDs permanentemente marcados como carregados após erro.

IMMEDIATE:

- clientes autorizados
- máquinas

7. OVERPASS
==================================================

Overpass possui alta variância confirmada.

NÃO permitir que uma consulta de água longa bloqueie a TELA.

A operação prioritária pode aguardar o enrichment necessário ao seu score,
mas o restante da interface já deve estar utilizável.

Preservar:

fallback synthetic_demo
+
proveniência correta

quando o provider falhar conforme as regras atuais.

NÃO inventar distância.

==================================================

- operação pode ser tentada novamente;
- IDs com erro não ficam marcados permanentemente como completos;
- UI não fica eternamente em "Calculando...".
